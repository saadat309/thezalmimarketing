# Dashboard and dynamic-route migration map

**Status:** Source route inventory is complete. Staging represents all current public route paths and dashboard route families, but route/feature presence is not full visual or behavioral parity. The Property editor uses source-derived conditional groups and fields, synthetic taxonomy/related-item options, server validation, and synthetic-only admin attributes; media controls remain disabled. File/Map editors still expose grouped synthetic fields. Queries has synthetic detail/read/unread/edit/delete/filter/bulk-delete/CSV workflows; Landing Page has editable section visibility/content/order/selection plus popup/video settings. Calculator Rates, Transfer Fees, Fixed Fees, Tax Rates, Fee Rules, Phases, Blocks, and Property Types now have source-derived editors sharing the public synthetic calculator configuration. Rates and Transfer Fees have synthetic CSV templates, validation previews, valid-row import, selected CSV export, and row/bulk deletion; uploads are capped at 512 KiB and 500 records. Fees, Tax Rates, Fee Rules, Phases, Blocks, Property Types, and taxonomy pages include selected-row CSV export. Fees and Tax Rates preserve source no-delete/key-lock behavior; Property Types keep fixed category/type and no add/delete; Phases and Blocks enforce scoped names/relationships and cascade sample dependent calculator records on deletion. Taxonomy map controls retain their synthetic relationship checks; Categories image storage remains deferred. Media uploads, formula edge coverage, and complete source visual comparison remain incomplete. The legacy dashboard's PDF export handlers inspected to date are toast-only placeholders; Calculator Fee Rules has no CSV import UI. Users/Profile are read-only by approved staging boundary. No production credentials, records, APIs, or storage are in scope.

## Staging implementation boundary

- The staging frontend remains `apps/staging-web/`; the isolated JavaScript API remains separate from the legacy PHP API and `workers/ai-worker`.
- Use versioned API contracts and repository interfaces. Start with deterministic synthetic in-memory adapters; later D1 persistence should replace the data adapter, not route/UI contracts. Media upload/storage remains a separate R2 design and is not part of this slice.
- The role is a single hardcoded `Admin` role shared by exactly two synthetic staging users. Do not build role management, invites, or user CRUD. Demo credentials are local-only and must not enter Git, plans, logs, or deployment configuration.
- Keep server-session and CSRF boundaries. The initial local session adapter is ephemeral and not suitable for deployment; any remote deployment requires a durable approved session store, rotated/independent secrets, and separate explicit deployment authorization.
- Staging CRUD and fixtures must be synthetic only. Inquiry/contact/email sending, uploads, production MySQL/API access, domain/DNS changes, Cloudflare resource provisioning, and `workers/ai-worker` remain out of scope.
- Calculator Rates, Transfer Fees, Fees, Tax Rates, and Fee Rules adapters mutate module-level synthetic fixtures only for the isolated local preview; this is intentionally ephemeral and must not be treated as deployable shared/persistent storage. Before any deployment, replace these with an approved durable adapter and verify Workers isolate/request semantics.
