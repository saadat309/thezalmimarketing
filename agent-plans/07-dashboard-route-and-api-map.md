# Dashboard and dynamic-route migration map

**Status:** Source route inventory is complete. Staging covers the mapped public routes and dashboard families, but route/feature presence is not full visual or behavioral parity. Local D1 now backs synthetic admin sessions/Profile, Property, Files, and schema-aligned Categories/Cities/Societies/Phases/Maps public-read/admin-CRUD slices; taxonomy and Map data use SQLite translations of the checked-in source tables with numeric foreign keys. Property data remains a transitional prototype schema, and other dashboard content remains in-memory. Property/File/Map forms, query and landing workflows, and calculator editors are source-derived but still need complete visual/behavioral comparison. Media uploads/storage remain disabled, users are read-only, and production records/APIs are out of scope. Rates and Transfer Fees have bounded synthetic CSV flows; the legacy Calculator Fee Rules PDF action is toast-only and has no CSV import UI.

## Staging implementation boundary

- The staging frontend remains `apps/staging-web/`; the isolated JavaScript API remains separate from the legacy PHP API and `workers/ai-worker`.
- Use versioned API contracts and repository interfaces. Local D1 adapters back synthetic auth/Profile, transitional Property/File prototypes, and source-schema-aligned taxonomy/Map rows. Slug-shaped Map API fields are translated to numeric SQLite foreign keys. A later import pipeline must preserve source IDs/relationships; Property and File prototypes are not yet import-ready. Remote D1 is a later, separately approved step after schema/query/free-budget review. Media upload/storage remains excluded from these data rows and requires a separate object-key migration design.
- The role is a single hardcoded `Admin` role shared by exactly two synthetic staging users. Do not build role management, invites, or user CRUD. Demo credentials are local-only and must not enter Git, plans, logs, or deployment configuration.
- Keep server-session and CSRF boundaries. Local sessions/Profile and Property records persist in the isolated Wrangler D1 simulator; this does not provision remote storage or authorize deployment. Any remote deployment requires separate approved storage, rotated/independent secrets, and explicit deployment authorization.
- Staging CRUD and fixtures must be synthetic only. Inquiry/contact/email sending, uploads, production MySQL/API access, domain/DNS changes, Cloudflare resource provisioning, and `workers/ai-worker` remain out of scope.
- Calculator Rates, Transfer Fees, Fees, Tax Rates, and Fee Rules adapters mutate module-level synthetic fixtures only for the isolated local preview; this is intentionally ephemeral and must not be treated as deployable shared/persistent storage. Before any deployment, replace these with an approved durable adapter and verify Workers isolate/request semantics.

## Recommended implementation slices

1. **Complete locally:** Add public synthetic Maps and Files list/filter APIs and replace their staging placeholders.
2. **Implemented locally:** Added loopback-only two-admin login/session/logout, a protected dashboard shell/home, a read-only two-admin account view, and versioned synthetic API auth/session gates. Direct API tests verify credential checks, seven-day cookies, concurrent independent sessions, CSRF, throttling, and local-host gating.
3. **Implemented locally:** Every mapped dashboard URL resolves in staging through the shared `$section` route. Users remain read-only; Profile supports self-edit of synthetic name/bio with email/role read-only. Property forms use the local D1 repository; File/Map editors group source-derived fields over synthetic fixtures. Queries and Landing Page have specialized synthetic workflows; Landing Page section order, visibility, titles, copy, selected items, popup delay, and embed URL save to the in-memory API. File/media upload remains disabled.
4. **Public frontend coverage:** `/`, `/about`, `/contact`, `/privacy-policy`, `/calculator`, `/properties`, `/properties/$slug`, `/maps`, and `/files` have staging routes. There is no current source Terms route. This measures route coverage, not exact design parity. Contact/newsletter actions remain disabled; media is placeholder-only; calculator values are fabricated and formula parity is not acceptance-tested.
5. **Next:** Translate the Property schema and related text tables to normalized SQLite/D1 with import-preserving numeric IDs/foreign keys, then plan the remaining content domains. Property/File prototype schemas are not ready for export/import. Continue field-by-field form comparisons; Rates and Transfer Fees have bounded synthetic CSV import. Treat toast-only legacy PDF handlers as non-output stubs and do not invent a Fee Rules import workflow. Keep uploads and transactional messaging disabled and production data out of scope.

The Property API and protected Property admin paths still share local D1 transitional rows, so synthetic publish/update/hide/delete changes affect subsequent public reads and ETags. Map and taxonomy APIs now share normalized local D1 source-shaped rows; Files still use a staging-specific representation. CMS/query/calculator persistence and deeper workflow semantics remain local previews. The route labels and basic edit controls are intentionally generic rather than a visual/form parity claim for every legacy module.

This sequence creates testable routes early without implying that the entire legacy dashboard has been ported. No route in this document authorizes deployment.
